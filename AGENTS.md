# Agent Constraints

These rules exist to prevent AI-assisted edits from destabilizing PIME/Rime host integration.

- Unlike mainstream Pinyin IMEs, Yime intentionally does not use bare digit keys for candidate selection. Base digits always remain composition keys, even while candidates are visible; ordinal selection uses Shift+1 through Shift+9. Do not add a digit-selection mode, a context-sensitive digit override, or a setting that switches digits between composition and candidate selection.
- Candidate labels must remain Shift-aware (`⇧1` through `⇧9`) through `setSelLabels`. `SetSelKeys` is retained only for legacy-host compatibility. Help and layout diagrams may show the physical Shift-layer keycaps `! @ # $ % ^ & * (`, but candidate-window ordinals must not revert to bare digits or continuous punctuation labels.
- Do not change native Rime candidate paging ownership without an explicit user request. `nativeBackend.UsesBackendCandidatePaging()` must keep returning `true`; real Rime sessions own their paging after activation and language-bar/menu clicks.
- Do not use Go-side candidate slicing as a shortcut to force the visible candidate count for native Rime sessions. Fix candidate count through Rime configuration/deploy/reload paths instead.
- Do not treat language-bar submenu depth as inherently unsafe. PIME may support nested menus, but changes to nested menu structure must be backed by a regression test that exercises the exact host click path.
- Before changing reverse lookup menu IDs, language-bar command IDs, candidate setting menu structure, or native backend click/activation behavior, add or update a regression test for the concrete failure path being protected. In particular, guard against clicking language-bar items such as "音元拼音" causing the host application to exit.
- The guard test `TestNativeBackendKeepsRimeOwnedCandidatePaging` is intentional. Do not weaken or remove it to make an unrelated candidate-window change pass.
- The Go-side `candidatePageSize` field must stay synchronized with Rime's `menu.page_size`. The sync mechanism works through `rimeState.PageSize`: `nativeBackend.State()` reads it from Rime, `applyStateToResponse` writes it back to `ime.candidatePageSize`, and `setCandidatePageSize` confirms the value after `reloadBackendForSchema`. Do not break this readback chain or introduce a separate Go-side page size that diverges from Rime's actual value.
- Do not assume Rime custom YAML keys are unquoted. Real user files may contain `"menu/page_size": 6`; any page-size read/write helper must support both quoted and unquoted `menu/page_size` keys or page-size changes will appear to "do nothing".
- When the candidate-count setting appears stuck, verify all three layers before changing logic: the language-bar command ID in `go_backend.log`, the actual files under `%APPDATA%\\PIME\\Rime`, and the installed runtime under `C:\Program Files (x86)\YIME`. Do not trust unit tests alone for this failure.
- Do not assume a source fix is live until you verify the installed `server.exe` and `rime_deployer.exe` were rebuilt, packaged, installed, and the running `PIMELauncher` and `server.exe` processes were restarted. Old installed binaries can make a correct source fix look ineffective.
- Do not assume language-bar submenu clicks always arrive as an integer top-level `req.ID` or `data.commandId`. Real host callbacks may report the clicked submenu item through `data.id` while the top-level button ID stays a string such as `reverse-lookup`; keep that compatibility covered by regression tests before refactoring command parsing.
- Do not "simplify" `commandIDFromRequest` by removing `data.id` fallback unless you have a host-level reproduction proving submenu clicks still reach `onCommand` correctly. Breaking submenu command decoding can make harmless reverse-lookup clicks look like host crashes or silent no-ops.
- When the reported bug is "language-bar click exits the host" or "menu click does nothing", verify the installed `C:\Program Files (x86)\YIME\go-backend\server.exe` timestamp changed and then reproduce once against the installed runtime before concluding the source fix worked. Source-only validation is not enough for TSF menu regressions.
- Do not simplify `Reinstall-PIME-Test.cmd` or `tools/templates/Reinstall-PIME-Test.cmd` back to uninstall-then-install only. The canonical reinstall flow must keep pre-flight (`dev-stop-pime.ps1 -Auto`), DLL-lock detection (exit code 2), and automatic in-place install fallback. `tools/refresh-dev-test-cmds.ps1` copies the template; edit the template, not an inline simplified generator.
- The Win32 PIMELauncher build requires the pinned `Rust_TOOLCHAIN=stable-i686-pc-windows-msvc` (set in the root `CMakeLists.txt`) plus Corrosion v0.6.1. Do not "fix" the build by unpinning the toolchain, removing `PIMELauncher/.cargo/config.toml`'s `build.target`, or downgrading Corrosion: with an x86_64 host toolchain, Corrosion leaks i686 target MSVC lib paths into host-side build-scripts (serde etc.), causing LNK4272 machine-type conflicts and 100+ unresolved externals. The prerequisite is `rustup toolchain install stable-i686-pc-windows-msvc`.
- Before diagnosing Rust as missing, check `C:\Users\tsaan\.cargo\bin\cargo.exe` and `rustup.exe` directly. This machine has repeatedly had a valid Rust installation while `%USERPROFILE%\.cargo\bin` was missing from `PATH`. Restore that user PATH entry and verify `rustup run stable-i686-pc-windows-msvc cargo --version`; do not reinstall Rust, change the pinned toolchain, or switch the Win32 build to an x64 host merely because `cargo` is not found in one shell.
- `rustup target add i686-pc-windows-msvc` on the default x64 toolchain is not an adequate substitute for the pinned i686 host toolchain. Development setup and CI must install the host toolchain with `rustup toolchain install stable-i686-pc-windows-msvc --profile minimal`; standalone PIMELauncher verification should use `rustup run stable-i686-pc-windows-msvc cargo test`.
- When `git`/`cmake` FetchContent fails with "Failed to connect to github.com:443" on this machine, it is not a transient outage. The WinINET system proxy (`localhost:1081`) is enabled but command-line git/cmake do not read it; set `$env:HTTPS_PROXY = "http://127.0.0.1:1081"` (and `HTTP_PROXY`) before reconfiguring. Do not delete `build/CMakeFiles` casually — that invalidates FetchContent stamps and forces a re-clone of corrosion, which needs the proxy.
- When `Reinstall-PIME-Test.cmd` reports `PIMETextService.dll is still loaded (often explorer.exe)`, that is the designed in-place-install path, not a failure. A fully clean uninstall+reinstall only happens after a Windows reboot releases the DLL. Do not force-kill explorer or force-delete the DLL to "unblock" the script.
- CodeIntegrity Operational events 3033/3077 mentioning `PIMELauncher.exe` loading `go-backend\server.exe` are audit records from Smart App Control (this machine runs SAC in enforce mode) about the unsigned dev binary — not evidence of a YIME crash or a broken install. The log also contains unrelated noise (Bonjour `mdnsNSP.dll`, Keyman). Check the event message paths before attributing failures to YIME, and remember unsigned binaries may be blocked outright on other SAC/WDAC-enforced machines; public release requires trusted signing.
- Before concluding the Win32 (`build/`) tree is broken, check whether its artifacts were simply cleaned: `dev-install.ps1` hard-requires `build/PIMELauncher/PIMELauncher.exe` and `build/PIMETextService/Release/PIMETextService.dll` and aborts early if missing. The fix is to rebuild `build/` (Win32, with the pinned toolchain), not to weaken the install script's asserts.
- YimeCore Broker transport connections own only the sessions they opened. EOF cleanup must release those sessions and their quota, but must not close sessions opened by another live connection from the same authenticated client process.
- Do not treat `TF_S_ASYNC` as a successful document edit. Registered-host UI and surface state may change only from the actual `DoEditSession` completion result; failed writes must leave host text unchanged, close candidate UI, and disconnect the surface for recovery. Keep both x64 and x86 delayed-lock and failed-write registered-host regressions.
- Before releasing a YimeCore language-bar object, detach every callback into `YimeTextService`. Hosts may retain the COM object after profile deactivation. Candidate popup code must likewise tolerate external HWND destruction by validating `IsWindow` and clearing the cached handle on `WM_NCDESTROY`.
- YimeCore trial upgrades must fully stage the new package before disturbing the old install. Preserve both the staging root and old install roots through preinstall; delete old roots only after new registration and runtime startup succeed. Rollback must restore COM/Profile, TIP, runtime config, Run value, uninstall key with original registry value kinds, and the previous running state.
- Elevated YimeCore trial maintenance must run under the same Windows SID that initiated it. Preserve `TargetUserSid` and `StateRoot` in elevation and uninstall commands. `repair-e6c-trial-autostart.ps1 -ValidateOnly` must read the actual registry value and reject missing or wrong values.
- YimeCore mutation idempotency includes the full ordered observation set. Reusing a mutation ID with changed context or segment observations is a conflict; do not discard observations to preserve legacy single-candidate retry compatibility.
- Treat canonical dictionary pronunciation as the only lexicon and syllable-code source of truth. Connected-speech support (tone sandhi, contextual neutral tone, erhua, particle allomorphy, assimilation, dissimilation, or other reductions) must be implemented as sourced and removable word- or phrase-level input aliases; do not rewrite `yime_pinyin_codes.tsv`, canonical dictionary pinyin, standard-pinyin annotations, or single-syllable base codes.
- Do not generalize contextual sound change from the fact that lexical neutral tone is supported. Keep lexical neutral tone separate from contextual weakening; do not add global `七`/`八` sandhi, third-tone, productive erhua, particle-character substitution, assimilation, dissimilation, or cross-word heuristics without a reviewed rule scope, exclusions, and evidence.
- Do not automatically insert or delete `儿`, or replace a particle character such as `啊` based only on neighboring pronunciation. Any candidate-text change must come from an explicit lexical or construction record with provenance.
- Any connected-speech alias must be derived into variable, full, and shorthand codes from the same canonical record and protected by a three-schema real-Rime regression. Read `docs/project/MANDARIN_CONNECTED_SPEECH_PLAN.md` before implementing or changing connected-speech behavior.
- Model connected-speech changes as position-preserving substitutions inside the canonical four-yinyuan syllable tuple, changing yinyuan height/tone grade or quality without inserting or deleting positions. Apply rules to stable yinyuan IDs and attributes before keyboard-layout projection, then derive all three modes. Reject any runtime alias that becomes longer than its canonical code in any mode.

## Offline lexicon and syllable toolchain

- Yime must not actively or passively import data from `Yime-python-prototype`, `Yime-prototype`, or any other Git repository. Large sources must be copied through an explicitly authorized one-time transfer into a content-locked directory outside every Git worktree; normal tools read only that independent directory through `YIME_LEXICON_EXTERNAL_ROOT`.
- Do not add sibling-repository defaults, `legacy_path` fallbacks, repository environment variables, symlink/junction workarounds, or automatic searches of parent directories. An exceptional cross-repository read requires a reviewed JSON under `tools/data_import_approvals/`, exact input IDs, a concrete authorization reference and reason, and an expiry no more than 31 days away. Do not weaken `check_repository_data_boundary.py`, `assert_data_source_allowed`, or `assert-data-source-boundary.ps1` to make an import pass.
- The in-repository offline chain is `attested tone-marked pinyin -> reviewed canonical inventory -> SyllableEncodingPipeline/YinjieEncoder -> four Yinyuan IDs -> canonical semantic code -> unique layout projection -> three Go codemode dictionaries`. Keep this dependency direction; never infer upstream pinyin or Yinyuan semantics from a generated Rime dictionary.
- Pianyin is not an equal-duration acoustic window, flat segment, raw waveform block, or verified natural-speech boundary. Yinyuan IDs identify abstract variables used to represent conditioned Pianyin; do not infer fixed sound values or durations from `M01`, `N01`, or tuple positions.
- Keep syllable admission instance-driven. Only attested or explicitly reviewed tone-marked syllables may enter the canonical inventory. Do not synthesize unattested five-tone combinations to make a gate pass.
- Existing rules must encode admitted syllables through the formal pipeline. Unknown forms must fail with evidence; never handwrite a four-Yinyuan code, Yinyuan ID sequence, `yinjie_code.json` row, pinyin spelling, or keyboard key as a repair.
- Pinyin semantics and physical layout are separate layers. The only editable layout source is `internal_data/manual_key_layout.json`; packaged `go-backend/input_methods/yime/data/yime_yinyuan_layout.json` and all mode dictionaries are generated, verified projections and must not be edited as alternative sources.
- Treat historical `v` spellings as compatibility input only. Registered form families such as `iu/iou`, `ui/uei`, `un/uen`, and `yo/io` must share the reviewed normalization rules; do not create parallel encodings.
- The rule catalog may document sources and transformations but must not contain Yinyuan IDs, code symbols, physical keys, or `vk_key` mappings. Those would create a second intermediate code table.
- Python under `tools/lexicon` and the migrated `syllable`/`yime` packages is offline tooling only. It must not import `pywin32`, `pynput`, Tk, or PyInstaller, must not enter the installer, and must not become a second Windows input runtime.
