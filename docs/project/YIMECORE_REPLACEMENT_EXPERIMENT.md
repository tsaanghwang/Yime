# Yime 自研栈并行替换试验

> 状态：E0、E1、E2-A、E2-B、E3-A、E3-B、E4-A、E4-B、E5-A、E5-B、E5-C、E5-D、E5-E、E5-F、E5-G、E6-A、E6-B1、E6-B2a、E6-B2b、E6-B3a、E6-B3b、E6-B4a、E6-B4b、E6-B4c readiness、E6-B4d 已通过；未批准切换任何生产组件
> 试验分支：`codex/yimecore-replacement-experiment`  
> 原则：先并行、后比较；逐层验收；失败即保留现状

## 1. 目的

本试验验证 Yime 能否逐步建立一套更适配四音元语音编码体系的自主实现：

1. `YimeCore`：词典索引、编码切分、候选搜索、排序、用户学习和语流音变路径；
2. `YimeBroker`：会话、进程隔离、协议、用户数据和运行维护；
3. `YimeTextService`：只负责 Windows TSF/COM、按键转发、预编辑、候选呈现和提交。

试验不是一次性重写，也不以复刻 librime/PIME 内部结构为目标。现有 Rime/PIME 链是生产基线和回退路径；只有全部门禁通过后，才允许逐项改变默认实现。

## 2. 当前、试验和目标结构

当前生产结构：

```text
PIMETextService.dll
    -> PIMELauncher / Go server.exe
    -> Yime Go TextService
    -> nativeBackend / cgo
    -> librime (C++)
```

试验期结构：

```text
现有 PIME/TSF 与 Go TextService（默认不变）
    -> CandidateEngine
       |- RimeAdapter -> librime       [生产基线]
       `- YimeCore                     [试验]
```

目标结构仅在试验全部成功后成立：

```text
YimeTextService.dll (C++，薄 TSF/COM 层)
    -> IPC
YimeBroker.exe (Go，会话、协议、进程和用户数据)
    -> CandidateEngine
       |- YimeCore                     [目标默认]
       `- RimeAdapter                  [迁移期回退]
    -> 只读静态索引 + 独立用户学习库
```

词典构建是旁路，不进入按键热路径：

```text
仓内规范真源 + YIME_LEXICON_EXTERNAL_ROOT 下的锁定来源
    -> Python 离线清洗、证据审计、音变派生
    -> Go 索引构建器
    -> 带版本和哈希的只读运行索引
```

## 3. 不可跨越的试验边界

- 不读取 `Yime-python-prototype`、`Yime-prototype` 或其他原型仓库。
- 不把大型词库、用户库、编译缓存或外部归档复制进 Git。
- 不逐函数翻写 librime/PIME；自主组件依据 Yime 需求、公开算法和黑盒行为契约实现。
- E0 至 E4 不替换或重构 TSF/COM 文本服务。
- 未通过切换门禁前，不删除 librime、不改变安装包默认后端、不迁移真实用户数据。
- 原生 Rime 会话继续拥有原生分页权，`nativeBackend.UsesBackendCandidatePaging()` 保持为 `true`。
- Base 数字键始终是编码键；候选直选仍由表层解释为 `Shift+1` 至 `Shift+9`。
- 语流音变继续从规范四音元记录派生；不得在按键回调中猜造词界、语气或韵律。
- 任何试验数据写入 `.tmp/yimecore-experiment/` 或独立外部目录，可完整删除回退。

## 4. 中立引擎契约

`CandidateEngine` 不依赖 PIME 请求类型、Rime session、Windows 句柄或具体词典文件格式。契约只描述：

- 编码输入、退格、清空；
- 当前原始输入和候选快照；
- 通过稳定候选 ID 选择并提交；
- 引擎能力声明，例如分页、句中光标、遗忘和用户同步；
- 可重放、可比较的确定性状态转换。

候选窗口标签、语言栏命令、TSF composition 和 IPC 都属于契约外的适配层。RimeAdapter 与 YimeCore 必须通过同一批中立轨迹测试，但允许对明确记录的产品改进产生不同候选排序。

## 5. 分阶段实现细目

### E0：边界、基线和最小内核（本分支启动项）

- 新增不依赖 PIME/Rime/Windows 的 `engineapi` 包。
- 新增纯 Go `yimecore`，只实现小型内存索引、前缀/整码查询和会话状态。
- 数字必须按普通编码字节进入 raw input。
- 新增固定轨迹、候选确定性、提交清空和错误边界测试。
- 新增合成词典性能烟雾工具；输出 p50/p95/p99/max 和正确性检查到 `.tmp`。
- 生产 `createRimeBackend` 工厂保持不变。

E0 只证明接口和最小热路径成立，不证明完整词典、组句或替换资格。

### E1：只读编译索引

- 设计版本化索引格式：文件头、模式、来源清单哈希、记录数、分区和校验和。
- Go 构建器只读取仓内合规真源或 `YIME_LEXICON_EXTERNAL_ROOT`。
- 运行时优先使用连续字节区、整数偏移和惰性文本解码，避免百万 Go 对象常驻。
- 完成变长、等长、省键三种模式的同源构建和交叉完整性检查。
- 对同一锁定输入连续构建两次，索引哈希必须一致。

E1 当前结果（100 轮、每模式 9 条精选整词探针）：

- 三个来源均为仓内现有生成词典，各读取 1,166,753 条记录；未读取原型仓库或外部 Git 仓库。
- 连续构建索引哈希分别为 full `81a27b...ffb1`、variable `159a873c...aada`、shorthand `b735b96b...9045ec`，每种模式两次构建完全一致。
- YimeCore/Rime 的 p95 比值约为 `0.20` 至 `0.38`，p99 比值约为 `0.19` 至 `0.38`，通过 `1.10/1.20` 门槛。
- 新鲜逐模式进程在相同探针负载后的 Working Set 比值约为 `0.39`、`0.85`、`0.86`，通过 `1.20` 门槛。
- 只读载荷采用流式完整性校验和 Windows 文件映射；索引文件、构建器和探针证据仍只写入 `.tmp`。

这些结果只覆盖整词/前缀查询，不包含切分、组句、学习、IPC 或 TSF，因此 E2 尚未开始，生产默认仍是 librime。

### E2：切分和动态组句

- 将连续编码表示为候选格图，不从生成词典反推规范读音或音元语义。
- 先实现确定性动态规划或 beam search，再引入上下文评分。
- 对每个候选保留输入区间、词典来源、规范路径和可选别名路径。
- 固定长句、歧义切分、退格、句中改选和连续提交轨迹。

E2-A 当前结果（100 轮、每模式 5 条精选句子探针）：

- 增量格图在每次追加按键时只扩展新终点，退格后可裁剪并从分叉位置继续；每条生成候选保留原始输入字节区间、词典码、文本和来源索引 ID。
- 三模式连续组句及撇号显式边界探针在 YimeCore 与真实 librime 中均全部通过，且必须由至少两个可审计片段生成。
- YimeCore/Rime 的 p95 比值约为 `0.33`、`0.47`、`0.52`，p99 比值约为 `0.32`、`0.44`、`0.48`，通过 `1.10/1.20` 门槛。
- 新鲜逐模式进程的 Working Set 比值约为 `0.42`、`0.93`、`0.92`，通过 `1.20` 门槛。

E2-B 当前结果：

- 中立事件可以用稳定句子候选 ID 和原始输入 `{start,end}` 聚焦既有分段；活动段只显示该编码区间的整码候选，不把显示汉字位置冒充原始输入光标。
- 选中活动段候选只保存 composition 内的区间约束并重算整句，不产生 commit；约束阻止其它切分边跨越已改选区间，前段或末段改选后其它分段、编码区间和来源均保持。
- 三模式真实完整词典均通过 `幅幅 → 逼逼` 首段/末段连续改选和最终显式整句提交，10 轮预验收的完整双改选 p95/p99/max 均约 `1.5 ms`，低于 `50 ms` 绝对上限。
- 现有真实 librime 的首/中/末段长会话和中段恢复全句回归继续通过；生产 `nativeBackend` 分页所有权守卫保持不变，现有 TSF 分段条没有接入试验内核。

E2-B 仍是两段中立内核试验：没有鼠标/TSF 接线、Broker 协议、安装态切换或与 Rime 匹配负载的相对延迟结论；原始输入一旦编辑，composition 内的分段约束即清除。上述边界不能被表述为已经完成生产替换。

### E3：排序与用户学习

- 分离系统静态分、上下文分和用户学习分，所有分值可解释、可版本升级。
- 用户库独立于静态索引，支持遗忘、备份、恢复、损坏隔离和原子升级。
- 先使用轻量统计方法；神经重排器若出现，只能是有时限、可关闭的可选层。
- 建立与现有 Rime 学习行为的并行观察，不直接迁移运行中锁定的 `*.userdb`。

E3-A 当前结果（每模式 200 个、每样本 100 次批量摊销的延迟样本）：

- 静态分、预留上下文分和用户分分别记录；一次显式选择可提升候选，遗忘后恢复静态顺序。
- 用户模型通过索引来源 ID 绑定，载荷带 SHA-256；保存采用同目录临时文件、落盘同步和平台原子替换。
- 三模式均通过“提升、保存重开、遗忘、损坏拒绝且不改写原文件、备份恢复”测试；学习快照不读取或迁移 Rime userdb。
- 学习排序相对无学习排序的 p95 开销比约为 `0.97` 至 `1.00`，通过 `1.10` 门槛；真实 Rime 三模式遗忘测试在隔离的临时用户目录中通过。

E3-A 仅使用整候选选择频次。E3-B 仍需定义上下文特征、衰减/封顶策略和 Broker 异步落盘协议；当前显式 `Save` 不能冒充生产级崩溃恢复。

E3-B 当前结果：

- 使用“前一提交文本、当前编码、当前候选文本”的结构键记录轻量 bigram 转移；候选证据分别显示静态分、上下文分、用户分和总分。
- 转移计数与全局选择计数共用来源绑定、载荷哈希、备份恢复及原子替换；遗忘候选时同时删除以该候选为目标的上下文转移。
- 三模式上下文排序相对静态排序的 p95 开销比约为 `0.99` 至 `1.01`，通过 `1.10` 门槛。
- 热路径采用预哈希结构键；试验中曾测得 full 模式字符串拼接键 p95 比值 `1.189`，该实现被拒绝且门槛未放宽。

E3-B 仍只是单阶上下文统计，没有自动衰减、跨应用隐私边界或 Broker 异步落盘。上述能力属于进入生产前的明确阻塞项。

### E4：语流音变原生路径

- 复用现有“规范四音元 -> 等位替换 -> 三模式投影”的唯一方向。
- 将已审定词/短语别名表示为同一候选的多条输入路径，避免重复候选污染。
- 只有在来源、边界和排除清单可验证时，才试验跨词或构式级动态规则。
- 与现有 Rime 附加词典逐阶段比较收益、碰撞、排序、延迟和回退结果。

E4-A 当前实现和结果：

- 只装入当前目标锁及各模块 manifest 已确认的四层：每模式 101 条 PSC 句子路径、131 条显式儿化句子路径、24 条 Stage5C 三声路径和 5,618 条 Stage6D `啊` 路径；没有从运行时输入推导或泛化规则。
- 核心和四个附加层分别编译为只读索引；组合来源 ID 绑定模式、核心来源和已启用模块。每个直接候选及句子分段保留具体模块来源，关闭模块只需在构造组合时省略该索引。
- 相同编码和候选文本只保留一项；规范路径与别名路径编码不同者并存。模块关闭后验证别名来源消失而规范路径仍可用；PSC 个头儿在关闭模块后仍可能由全核心动态切分得到相同文本，证据因此区分“模块路径已移除”和“文本仍可由其它路径生成”。
- 预验收发现低权重 PSC 路径可能位于第 2 页，因而补充 YimeCore 自有 `PageNext/PagePrevious` 中立事件和分页状态。裸数字键语义未改变，原生 Rime 分页归属也未改动。
- 小型附加索引使用稀疏二字节前缀桶，百万级核心继续使用稠密桶。20 轮预验收中，YimeCore/Rime p95 比值为 `0.86/1.00/0.91`，Working Set 比值为 `0.45/1.02/1.00`，均通过既定门槛。

E4-A 不包含 Stage3 研究态语境轻声、生产性儿化、跨未知词界规则、候选文字改写或生产配置开关。只有既有审定词典记录进入组合索引；后续 E4 项若没有同等闭合的来源、边界和排除证据，必须停在审计阶段。

E4-B 在 E4-A 精选探针之上增加全量直接路径审计：逐模式枚举四个模块索引的全部 5,874 条记录（合计 17,622 条），逐条核对编码、候选文本、权重和模块来源，并在省略该模块后确认相同模块来源不再存在。当前预验收中 17,622 条均可达、无来源遮蔽；性能和内存仍在全量审计开始前按与 Rime 相同的精选探针负载采样，避免用“YimeCore 全词典遍历后、Rime 仅 5 条探针后”的不等负载快照作比较。

### E5：自研中层 / Broker

- 在 YimeCore 已可用后，才冻结版本化 IPC 协议。
- Broker 运行在普通用户权限下，负责会话、超时、崩溃隔离、索引切换和用户数据。
- 安装、注册和升级提权仍由安装器处理；Broker 不成为提权代理。
- 先让现有文本服务连接新 Broker，同时保留现有 server.exe 回退。

E5-A 当前只冻结与传输无关的第 1 版引擎协议，并在进程内比较严格 JSON 编解码/调度与同一 YimeCore 的直接调用：

- 客户端身份由未来传输适配层在消息外提供；协议请求不含可自报身份。会话绑定该身份，并限制全局 64 个、单客户端 4 个活动会话。
- 每会话序号严格递增；跨客户端访问、重放/乱序、未知字段、超长消息和非法操作均产生稳定错误码，不进入引擎。
- 单会话调用串行化。引擎 panic 或 50 ms 超时会逐出该逻辑会话；其它会话继续可用，关闭后活动会话计数归零。
- 三模式均使用 1,166,753 条记录的完整只读索引和 E2 长句轨迹比较直接调用与 Broker 路径；门禁预先固定为整轨迹 p95/p99 比值不超过 `2.0/2.5`、单消息 p95/p99 不超过 `2/5 ms`、单次不超过 `50 ms`、Broker 增量分配不超过 `64 KiB/消息`。

E5-A 不连接 PIME、TSF、命名管道或安装态组件，也不改变 `server.exe`、PIMELauncher 和默认 Rime 工厂。进程内超时只能把会话从调度器逐出，不能强制终止已经阻塞的 Go 调用；真正的硬终止/重启、异步用户模型落盘和崩溃一致日志属于后续独立 Broker 进程试验，不能由 E5-A 的通过替代。

E5-B 将同一协议和调度器装入独立的试验 `YimeBroker.exe`，由监督试验通过匿名管道逐消息请求/响应：

- 三模式仍以同一完整索引和 E2 长句轨迹比较直接调用与独立进程结果，候选状态和 commit 必须逐项一致。
- 监督端对每个响应设置 `100 ms` 上限；试验子进程在指定请求前退出或停滞时，必须被检测、终止并以新会话重启，随后完整重放当前轨迹。
- 进程门禁在首次正式基线前固定为整轨迹 p95 比值不超过 `4.0`、单消息 p95/p99 不超过 `10/20 ms`、单次不超过 `50 ms`、Broker Working Set 不超过 `128 MiB`、退出或卡死恢复不超过 `2 s`。

E5-B 仍不是生产接线：匿名管道的单一监督身份由启动参数在消息外绑定，但真实命名管道身份适配、生产监督生命周期、用户模型崩溃一致落盘、索引热切换和 TSF/PIME 并列接入均未实现。`YimeBroker.exe` 只构建到 `.tmp` 证据目录，没有进入安装包或默认启动路径。

E5-C 为独立 Broker 增加可选的用户模型快照和写前日志：

- 每次选择产生带单调 generation 的学习变更；Broker 写入绑定精确索引来源、前一记录哈希和当前记录 SHA-256 的严格 JSON 日志，并在向会话返回 commit 前完成 `fsync`。
- 模型快照继续使用确定性载荷哈希和同目录原子替换。后台快照不清除日志；重启时先验证完整哈希链，再跳过快照已覆盖的 generation，并重放更新记录。
- 崩溃留下的不完整末行视为未确认尾部，可截断到最后一个完整同步记录；完整但解码、来源、generation、链或记录哈希不符的日志一律拒绝，不自动修改。
- 试验必须在快照尚不存在时强制结束真实 Broker 进程，仅从日志恢复全部已确认学习、候选提升和 generation；随后清洁退出生成快照，并验证损坏日志副本不能打开。

E5-C 的门禁在正式基线前固定为持久化选择 p99 不超过 `20 ms`、单次不超过 `50 ms`、崩溃检测、重启、日志恢复和候选验证合计不超过 `2 s`。它采用持久化先于响应的语义；若进程恰好在日志同步完成后、响应送达前退出，恢复后可能保留一项调用方不知道是否成功的学习记录。E5-F 已通过持久化请求幂等标识解决新调用方的重复学习风险；未提供标识的旧调用仍不能通过丢弃已同步日志规避这个窗口。

E5-D 为 Broker 增加带代际租约的索引管理器和独立控制清单：

- 候选索引在发布前必须匹配声明的文件 SHA-256，通过索引内部载荷校验、模式核对和可选行为探针；任何一步失败都只增加拒绝计数，active 代际不变。
- 发布只原子替换新会话取得的 active 指针。已经打开的会话继续租用原代际和映射；会话正常关闭、panic 或超时调用最终退出后释放租约，避免索引仍被调用时解除映射。
- 管理器保留一个 previous 代际供显式回滚。回滚只交换 active/previous，新旧既有会话仍留在各自代际；第三代发布后，不再保留且没有会话引用的旧代际才关闭。
- 独立 Broker 可观察严格 JSON 控制清单，并原子发布包含请求 ID、接受/拒绝、错误、active/previous 版本、来源 ID、哈希、会话引用数和计数器的状态文件。引擎协议响应同时回报会话绑定的 index version，便于验证切换期间没有会话漂移。

E5-D 使用完整核心索引作为 v1、使用已审定 Stage5C 三声覆盖索引作为不同哈希和不同候选行为的 v2：错误哈希必须留在 v1；有效切换后旧会话仍为 v1，新会话必须为 v2 且命中审定探针；回滚后 v2 会话仍可用，而随后新会话重新取得 v1。覆盖索引只用于证明不同内容代际的切换机制，并不表示它可以脱离核心词典单独成为生产索引。

E5-E 在不接入生产传输和宿主的前提下，对已经完成的核心与 Broker 能力作并发长稳压测：

- 每种编码模式同时运行 4 个独立 `YimeBroker.exe` 子进程（各绑定独立可信客户端身份）和同一共享 Dispatcher 上的 8 个独立可信客户端；每客户端只持有一个串行会话，不以并发调用同一会话制造协议外负载。
- 正式负载持续至少 120 秒，并至少完成 100,000 个严格 JSON 请求。所有客户端循环重放同一 E2 长句探针，要求候选代码、文字、精确标志和最终提交全程正确，关闭后共享 Dispatcher 活动会话必须归零。
- 内存基线之前先让全部客户端以相同并发拓扑循环完整探针至少 5 秒，使所有句子路径、会话缓冲和进程堆进入实际工作状态；预热请求不计入正式吞吐和延迟样本。
- 进程内与匿名管道请求分别统计延迟；门禁沿用 E5-B 的 `p95 <= 10 ms`、`p99 <= 20 ms`、单次 `<= 50 ms`，总吞吐不低于 `500 请求/秒`。
- 延迟证据使用固定大小、10 微秒粒度的流式直方图；百分位取所在桶上界，单次最大值保留原始纳秒值。证据收集内存因此不随请求总数增长。
- 负载三分之一处强制结束一个独立 Broker，再以相同锁定索引和可信身份重新启动并重放当前探针；恢复不超过 2 秒，且恢复期间其它客户端必须继续完成请求。
- 每秒采样试验驱动及所有 Broker 的总 Working Set/Private Bytes。峰值 Working Set 不超过每个实际进程 `192 MiB` 的总预算，预热后到结束的总 Working Set 增长不超过 `96 MiB`。

E5-E 的多客户端并发由共享 Dispatcher 直接承受；多个独立 Broker 同时提供真实进程和匿名管道压力。它不声称匿名管道已经成为生产多连接传输，也不替代后续命名管道身份绑定、TSF 宿主和安装态验收。

E5-F 消除 E5-C 中“日志已经同步、响应尚未送达”窗口的重复学习风险：

- `select` 请求可携带 8 至 128 字节的 ASCII `mutation_id`；Broker 将其原样回显，只允许在选择操作中使用，并拒绝不合规标识。
- YimeCore 把标识、候选身份和 generation 一同写入哈希链日志，在内存模型和原子快照中保留已应用请求账本。同一标识重试相同候选会再次返回提交但不增加学习次数；同一标识改投其它候选会稳定失败。
- 真实进程试验在日志 `fsync` 和模型变更完成后、响应写管道前强制退出 Broker；重启、重放输入并以相同标识重试后必须取得原提交，最终 generation 仍为 1，恢复不超过 2 秒。

幂等语义只对提供 `mutation_id` 的新调用方生效；未提供标识的旧调用继续保留 E5-C 的至少一次持久化语义。E5-G 已使 WAL 有界；请求账本的时间清理仍须先制定调用方重试窗口，不能通过丢弃尚可能重试的标识缩短账本。

E5-G 为用户模型增加有界 WAL、可逆快照迁移和压缩崩溃恢复：

- 后台累计达到配置的 mutation 间隔后，先原子发布包含全部学习和幂等账本的 v2 快照，再关闭旧 WAL，随后以写穿透原子替换发布空 WAL，最后重新打开追加句柄。任何失败均优先恢复当前磁盘上的旧或新 WAL；无法重新打开时停止接受后续持久化变更。
- 首次打开 E5-F 的 v1 快照时，在任何 v2 写入前生成并验证独立 v1 回滚快照。当前读取器同时接受 v1/v2，正常保存升级为 v2；回滚快照仍包含迁移前的学习和幂等账本，可由 E5-F 版本读取。
- 三模式分别在“v2 快照发布后”“旧 WAL 关闭后”“空 WAL 原子替换后”强制结束真实 Broker。每一处都必须恢复排序和旧 `mutation_id`，追加两项新学习后再次压缩到 0 字节 WAL，最终 generation 精确为 4，并在 2 秒内完成。

WAL 因压缩间隔而有界；幂等账本仍以一百万模型项目的硬上限有界，不自动按时间删除。定义调用方最长重试期之前不得清除旧标识，否则会重新引入 E5-F 已消除的重复学习窗口。v1 回滚快照代表首次迁移前状态，选择回滚会有意放弃只存在于 v2 阶段的新学习。

### E6：自研表层 / TextService

- 最后实现薄 C++ TSF/COM 层，不承载词典、音变、排序和用户学习。
- 以现有 PIMETextService 为黑盒行为基线，重新验证 x86/x64、候选窗、语言栏、失焦、应用退出和重启路径。
- 新旧文本服务不得共享注册标识或安装目录进行破坏性覆盖；采用并列试装和独立卸载。

E6-A 已完成表层之前的生产形态 IPC 门禁，但尚未实现或注册新 TSF：

- `YimeBroker.exe` 可选择监听本机 Windows 字节流命名管道，同时接受多连接；管道 DACL 只允许当前用户和 Local System，并以 `PIPE_REJECT_REMOTE_CLIENTS` 拒绝远程客户端。第一个实例使用 `FILE_FLAG_FIRST_PIPE_INSTANCE`，防止同名服务被抢占。
- 每条连接的可信身份由服务端通过 `GetNamedPipeClientProcessId`、客户端进程令牌 SID 和 PID 绑定，协议继续严格拒绝请求 JSON 中自报的身份字段。连接总数和同一客户端连接数均有独立上限，达到总上限时先等待槽位再创建新实例。
- 独立 C++17 探针分别构建为 x86 和 x64，不链接 PIME、Rime 或 YimeCore。三模式各由四个独立进程并发验证数字编码 `2jru`、候选稳定 ID、幂等选择、提交、严格协议和延迟；另以不同 PID 验证会话不可越权，并在强制结束、重新启动 Broker 后重放同一轨迹。
- E6-A 预验收的每模式 48,012 个并发请求均无协议或提交错误，最差单客户端 p99 为 0.24 ms、最差单次为 1.42 ms，重启后完成连接和 200 轮重放为 180–186 ms。门禁仍采用单次小于 50 ms、重启小于 2 秒；正式证据需在干净提交上重跑并以其数值为准。

E6-A 不处理候选窗、语言栏、焦点/失焦、TSF composition、注册、安装或签名；这些仍属于 E6-B 及发布验收。现有 `PIMETextService.dll`、PIMELauncher、Go TextService、默认 Rime 工厂、注册标识和安装目录均未改变。

E6-B1 已建立不注册、不接 Broker 的最小 C++ COM/TSF 外壳：

- `YimeTextServiceExperiment.dll` 采用与 PIME 及未来生产服务均不共享的试验 CLSID、Profile GUID 和语言栏 GUID，只导出 `DllGetClassObject`、`DllCanUnloadNow`，不导出 `DllRegisterServer`。
- x86/x64 分别验证类工厂、拒绝 aggregation、`ITfTextInputProcessorEx` 与 `ITfKeyEventSink` 查询、无效激活拒绝、1,000 次重复创建/释放和最终可卸载。
- 键契约单独锁定：无 Shift 的 `0` 至 `9` 全部是 composition 键；只有 `Shift+1` 至 `Shift+9` 是候选 ordinal；`Shift+0` 不是候选 ordinal；窗口标签固定为 `⇧1` 至 `⇧9`。
- B1 外壳即使被误加载也始终报告按键未被吃掉。只有 E6-B2 同时完成 Broker 状态转换和 TSF edit session 后，才允许相应键返回 eaten。

E6-B1 没有 composition、候选 UI、语言栏、焦点状态或安装入口，不能冒充可用输入法。它只是把 COM 生命周期、独立身份和最重要的数字键契约先从后续功能中剥离出来验证。

E6-B2a 已在 TSF edit session 接线前完成 C++ 表层到 Broker 的会话和按键桥：

- `BrokerClient` 只发送协议 v1 的 open/apply/select/close，不发送客户端身份；候选选择使用 Broker 返回的稳定 candidate ID 和独立 mutation ID。

- 三模式分别用 x86/x64 C++ 桥输入 `2jru`，验证首键 `2` 保留在 raw composition、首候选稳定为同一文本、`Shift+1` 提交该稳定候选并清空 raw input；主动断开后再次输入必须失败且不报告 handled。
- 每模式强制结束并重新启动 Broker 后重新执行相同桥接轨迹，预验收均在 107 ms 内完成。现有 COM 生命周期和 Shift 标签回归同时继续通过。

E6-B2a 仍在 `ITfContext` 之外运行。把成功的 `BrokerUpdate` 通过同步 TSF edit session 写成预编辑/提交，并在失败时保持宿主文本不变，是 E6-B2b 的独立门禁。

E6-B2b 已把 Broker 状态写入真实 TSF 文档上下文：

- 表层仅在 Broker 操作成功后请求同步 `TF_ES_READWRITE` edit session；edit session 成功写入或提交后才报告 eaten。写会话失败会关闭该试验 Broker 会话并报告未吃键，避免宿主文本与内核状态继续分叉。
- raw input 通过 `ITfContextComposition::StartComposition` 建立预编辑范围并逐键替换；稳定候选提交先替换 composition range、移动 selection，再结束 composition。

- 三模式分别由 x86/x64 DLL 在真实 `ITfContext` 中验证 `2`、`2j`、`2jr`、`2jru` 的预编辑进展、`Shift+1` 提交、composition 消失和第二轮会话复用；Broker 强制重启后重放同一轨迹。

E6-B3a 已验证宿主主动终止 composition 的恢复边界：

当前 B4c 只完成能力和 fail-closed 门禁。只有在提权进程中完成 x86/x64 的真实 register/status/unregister 循环，并由注册后的宿主自动派发按键与焦点回调，才可把 B4c live 门禁标为通过。

E6-B4d 已实现活动 composition 的跨 `ITfContext` 隔离：

- 表层记录 composition 所属的 `ITfContext` 和 `ITfDocumentMgr`。只要旧 composition 尚未结束，来自其它 context 的 `OnTestKeyDown` 和 `OnKeyDown` 一律不接管，不能把 Broker 状态写入新文档。
- `OnSetFocus(TRUE)` 会读取线程管理器当前文档；焦点不属于旧 composition 时继续隐藏原候选 UI，返回原文档后才恢复显示。
- full、variable、shorthand 的 x86/x64 六条路径各建立两份真实 TSF 文档图，确认新文档保持空白、旧预编辑保持 `2jru`、候选不串窗，并在返回旧文档后正常提交。

B4d 验证了跨文档状态不会互相污染，但焦点回调仍由测试经真实 key-sink 接口触发；系统自动派发和真实应用进程切换仍须 B4c live 注册门禁验证。

E6-B5 已实现宿主要求文本服务自绘时的最小候选窗口和鼠标选择路径：

- `CandidatePopup` 是无图标、无皮肤的 Win32 `WS_EX_NOACTIVATE` tool window，只使用系统字体和系统颜色。窗口最多显示九项，文本继续来自 `CandidateListUIElement` 的 `⇧1` 至 `⇧9` 标签，不产生裸数字候选序号。
- `BeginUIElement` 注册失败时由自身窗口显示；注册成功时严格服从宿主返回的 owned-window 决策。窗口不取得键盘焦点，失焦、跨文档、提交、外部终止和停用都会隐藏或销毁。
- composition 更新的同一次 TSF 写 edit session 会尝试用 `ITfContextView::GetTextExt` 取得预编辑范围。无 context owner 的合成上下文明确记录无法取得文本范围，再降级到上下文 caret、上下文窗口或系统指针位置；窗口始终钳制在所在监视器工作区内。
- 鼠标松开只接受候选内容行，映射为同一个 `Shift+1` 至 `Shift+9` ordinal，再由 `SurfaceSession` 使用 Broker 稳定 candidate ID 提交；点击边框不触发选择。裸数字键规则没有改变。
- full、variable、shorthand 的 x86/x64 六条路径均验证自有候选窗可见、焦点与文档隔离、恢复显示、鼠标首项提交以及原有键盘提交和强制终止回归。

B5 的无 owner 合成上下文不提供可用 `GetTextExt`，因此不能把降级锚点冒充真实应用定位通过。注册后的系统按键汇派发、真实应用文本范围定位和自动焦点回调仍必须在提权的 registered-host 门禁中验证；通过前不批准默认切换。

E6-B6 已建立提权注册后的真实 TSF 宿主门禁：

- 独立 `YimeRegisteredHostTests` 不加载 DLL、不查询试验类工厂，也不直接调用 `ITfKeyEventSink`。它通过系统已注册 Profile 切换当前 TSF 语言和激活试验 TIP，再从 `ITfKeystrokeMgr` 派发按键。
- 宿主实现最小内存 `ITextStoreACP` 和同步锁协议；composition 写入、selection、候选提交和 `GetTextExt` 全部经 TSF 与宿主 text store 往返。候选窗左上位置必须精确跟随宿主返回的文本范围底边，不能落入 caret 或鼠标降级路径。
- 激活 Profile 后重新聚焦文档，要求 foreground key sink 出现；切换到第二个 `ITfDocumentMgr` 时由系统自动派发焦点与 composition 终止事件。若宿主保留旧 composition，新文档按键必须隔离，候选窗须隐藏并在返回原文档后恢复；若宿主终止 composition，候选 HWND 和旧 Broker 会话必须清理，下一次合法组合键必须建立新会话并从空状态开始，不得继续旧 composition。
- 注册和宿主运行始终包在精确注销的 `finally` 中；x64 与 x86 依次使用各自 COM 视图，三种编码模式分别启动独立 Broker，任何失败后仍须等待 TSF 枚举收敛并通过 `verify-absent`。
- Windows 8 以后 language-bar `AddItem` 的 S_OK 允许代表静默忽略；宿主只在 HRESULT 为 S_OK 且返回非空接口时记录 accepted，不再解引用空指针。该辅助观察不替代按键、composition、候选窗、焦点和定位主门禁。

B6 仍是专用内存 text-store 宿主，不冒充第三方桌面应用或签名安装包验收。下一步是独立目录的并列试装、卸载回滚和安装态宿主验证；通过前默认 Rime/PIME 路径保持不变。

E6-B7 将 B6 已锁定的 Broker、三份索引以及 x86/x64 表层组件组装为独立试验包：

- 包清单固定每个文件的相对路径、字节数与 SHA-256；写入 Program Files 的独立试验目录后再次逐文件核验，注册和宿主测试只能使用安装态路径。
- x86/x64 继续依次使用各自 COM 视图，三种编码模式都要从安装态 Broker 与索引完成真实 Profile 激活、按键汇、文本定位、焦点和候选提交路径。
- 试验组件使用与生产 YIME/PIME 不同的 CLSID、Profile GUID 和安装目录；任何路径都不覆盖默认 Rime/PIME 组件。
- 注销在每种架构的 `finally` 中执行，最后只在安装根目录携带匹配的包身份清单时递归移除该精确目录；两种注册视图和安装树都必须零残留。
- 试验包只存在于 `.tmp` 证据目录和临时 Program Files 试装目录，不把三份大索引或词库复制进 Git。

B7 仍是未签名的试验目录，不等同于公开 MSI/签名发布包，也未替代第三方桌面应用的真实交互验收。

E6-B8 完成独立试装目录上的第三方桌面应用交互验收：

- 文本服务在未设置环境变量的普通宿主中使用固定默认端点 `\\.\pipe\YimeBroker.YimeCoreTrial.v1`；环境变量只保留给测试和监督进程覆盖。宿主强制结束 composition 后，表层保留端点但关闭旧会话，下一次合法组合键在 100 ms 短门限内重新连接；显式 `Close` 和停用仍永久清除端点。
- `repoint` 只在既有 Profile 和三项 TSF category 完整时创建或改写当前位宽 COM 路径，支持旧 DLL 仍被宿主占用时切到新的版本化安装目录，不删除、不重注册全局 Profile。x64 与 x86 COM 视图必须同时指向同一独立试装根目录。
- Microsoft Word x64 真实交互按 `2 -> File 后台 -> 返回文档 -> 2 -> Shift+1` 执行：首次候选窗出现；进入后台后 Word 将旧 composition 作为原始 `2` 结束；返回后第二个 `2` 建立新会话并再次显示候选；`Shift+1` 提交首项“其”。裸数字始终是组合键，候选序号继续是 `⇧1` 至 `⇧9`。
- B8 证据同时核验 staged/install 两棵目录的逐文件 SHA-256、两个 COM 视图、Word 实际加载模块、安装态 Broker 路径和默认管道命令行；交互观察由明确开关签注，机械路径与哈希验证不能由观察文字代替。
- 所有试装文件和证据留在 `.tmp` 与独立 Program Files 试验目录；没有读取原型仓库，没有把索引或大词库加入 Git，默认 Rime/PIME 注册和安装保持不变。

B8 证明当前自研 Broker/表层已能在 Word 中完成宿主终止后的新会话恢复，但仍是未签名试验包；x86 桌面 UI 只由注册式内存宿主覆盖，公开签名安装包和更多第三方应用矩阵仍属于发布门禁，而不是本阶段能力阻塞。

### E7：切换与退役

- 只有 E0 至 E6 全部门禁通过，并完成签名安装包真实宿主验收，才提交默认切换提案。

- 至少一个稳定发布周期保留 RimeAdapter 和旧安装包回退证据。

## 6. 比较矩阵与成功门禁

所有比较必须使用同一机器、同一锁定词典快照、同一输入轨迹和相同候选上限。

| 维度 | E0/E1 门禁 | 最终切换门禁 |
|---|---|---|
| 正确性 | 固定轨迹状态转换 100% 通过 | 三模式、长句、改选、学习和音变验收 100% 通过 |
| 确定性 | 同输入结果和构建哈希一致 | 安装前后索引及行为证据一致 |
| 延迟 | 记录 core p50/p95/p99/max，不据合成数据切换 | 真实轨迹 p95 不比 Rime 基线慢 10% 以上，p99 不慢 20% 以上 |
| 卡顿 | 合成重放无错误和非预期分配增长 | 100,000 次真实轨迹重放无单次引擎处理超过 50 ms |
| 内存 | 记录索引构建和查询分配 | 启动完成 RSS 不比当前基线增加 20% 以上 |
| 恢复 | 删除 `.tmp` 即回退 | 引擎、Broker、文本服务均有独立回退开关和安装包 |
| 数据 | 只用小夹具或锁定来源 | 不读原型仓库、不提交大词库、用户数据升级可逆 |

相对阈值只能在取得第一份真实基线前调整；取得基线后，任何放宽都必须单独评审，不能为了让试验通过而修改。

## 7. 证据目录

每轮试验写入独立目录：

```text
.tmp/yimecore-experiment/<stage>/<timestamp>/
    manifest.json
    correctness.json
    latency.json
    memory.json
    source-hashes.json
    comparison.json
```

证据必须记录 Git commit、dirty 状态、Go 版本、OS/架构、索引来源 ID/哈希、轨迹 ID/哈希和引擎实现 ID。合成 E0 烟雾不能冒充真实 Rime 对照结果。

## 8. 当前退出条件

E0 已满足以下条件：

1. 中立契约和最小 YimeCore 不导入 PIME、Rime、cgo 或 Windows 包；

3. 合成重放产生结构化性能证据；
4. 现有 Rime 默认工厂和原生分页守卫未改变；
