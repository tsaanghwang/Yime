# 阶段 4A：儿化音元与键位投影

## 1. 结论

阶段 4A 把“儿化后实际存在的音元”和“用户按下的物理键”拆成两个层次：

1. 派生儿化音元保存音质、鼻化、卷舌和调级等语音属性；
2. 键位类只保存一次输入动作的调级类别；
3. 多个不同的派生音元可以投影到同一个共享键位类；试运行阶段也允许派生音元使用明确登记的专用
   Shift 键；
4. 共享键位类可借用现有 `M22/M23/M24` 的布局位置，专用键只记录物理输入动作，两者都不得冒充
   派生音元的实际音值。

因此，工程可以继续增加和修订儿化音元，而不必为每个新音值增加一个物理键，也不必重排现有布局。

## 2. 当前试点边界

当前显式儿化来源包共有 131 条记录：

- schema 2 来源包中的 131 条现均为 `feature_projection_ready`，`suffix_only_encoding_pending` 已清零；
- 每条就绪记录都保存规范附着音节的基础四音元元组、规则 ID 和逐位置卷舌/鼻化特征改写；运行端
  不再读取表层 IPA 分类，也不再用附着韵母临时推断融合类型；
- 131 条运行融合路线中，65 条从三种核心词典继承相同权重，66 条从 PSC 低频外围层继承精确儿缀
  记录的固定权重 `1`；
- 核心权重记录在融合层保留儿缀、融合两条路线，PSC 低频记录的儿缀路线留在外围层，融合层只补
  融合路线；正式融合附加产物因此每模式 196 条路线、三模式合计 588 行。

阶段 4A 当时没有新增或删除运行词条；随后 PSC 外围来源为原先延期的 14 条提供了可追踪低权重，
现已只补入其融合路线，没有改变候选文字或核心排序。用户已在安装态验证过“一阵儿”和“小曲儿”
的融合路线；其余宿主行为仍按既定回归计划继续验证。

## 3. 音元与键位结构

机器真源为 [erhua_sound_key_projection.json](erhua_sound_key_projection.json)。当前登记：

| 类别 | 数量 | 状态 | 用途 |
|---|---:|---|---|
| 口腔中央卷舌音元 `[ɚ]` | 3 | `runtime_pilot` | 高、中、低三个调级，供 4 类融合儿化使用 |
| 口腔 `a˞` 音元 | 3 | `runtime_pilot` | 临时投影到基础 `a` 三调键的 Shift 层 `F/D/S` |
| 后中 `ɤ˞` 音元 | 3 | `runtime_pilot` | 临时投影到基础 `o/ɤ` 三调键的 Shift 层 `R/E/W` |
| 鼻化 `ã˞` 音元 | 3 | `runtime_pilot` | 低、中、高调试用 `Q/T/Y` |
| 归并鼻化后中 `ɤ̃˞` 音元 | 3 | `runtime_pilot` | 高、中、低调试用 `V/C/X` |
| 后高 `u˞` 音元 | 3 | `runtime_pilot` | 高、中、低调试用 `P/A/Z` |
| 共享输入键位类 | 3 | 布局载体 | 高、中、低分别借用 `M22/M23/M24` 的键位 |
| 专用 Shift 键位类 | 15 | 临时试点 | 五组三调派生音元各使用一组明确登记的 Shift 键 |

中间层不保存“表层类 → 音元家族”的编码指令，而保存如下可检验数据：

1. `attached_syllable_source_yinyuan_ids`：来自规范拼音编码链的四位置基础音元；
2. `feature_rule_id`：说明该显式韵母采用哪组位置规则；
3. `feature_rewrites[]`：逐项给出位置、原音元 ID、基础音元 ID，以及 `rhotic`、`nasalized`；
4. Windows 端根据 `(base_yinyuan_id, rhotic, nasalized)` 唯一解析派生音元 ID，再从同一派生元组
   计算等长、变长、省键码。

`M22/M23/M24` 本身就是中央卷舌音元，因此中央化结果复用这三个既有 ID；其余口腔 `a˞`、后中
`ɤ˞`、鼻化 `ã˞`、鼻化后中 `ɤ̃˞`、后高 `u˞` 共 15 个组合解析为 `R04`—`R18`。表层 IPA
仍可作为人工审校和显示说明，但生成器既不读取儿化草稿，也不根据表层字符串归纳音元。

当前 131 条记录实际使用 15 个特征规则 ID。三种模式中的融合码均从派生元组重新计算；三套规范
核心码未使用 `Q/T/Y/V/C/X/P/A/Z`，所以当前样本没有与既有核心码形成新增 Shift 码重合。此结论
只说明当前显式样本无键码碰撞，不代替安装态键感和宿主兼容性观察。

## 4. 派生门禁

`yime-erhua-mixed-derive` 在写出词典前必须完成以下检查：

1. 基础音元、特征组合、派生音元 ID、键位类和调级均唯一且完整；
2. 借用基础音元载体的共享键位类必须接收至少两个不同音元；专用 Shift 键位类必须与基础布局及
   其它专用键无碰撞；
3. 所有载体 ID 和保留位置 ID 均存在于当前 `yime_yinyuan_layout.json`；
4. 逐条把所有路线、所有模式的 Yinyuan ID 重新投影成键位字符串，并与来源包中的编码一致；
5. 131 条融合路线必须逐条从显式基础元组和特征改写得到派生元组；缺规则、重复改写位置或原音元
   不匹配均立即失败，不得退回表层分类推断；
6. 运行试点只能引用 `runtime_pilot` 音元，任何 `research_only` 音元进入导出即失败；
7. 融合路线在变长、等长、省键任一模式中都不得比儿缀兼容路线更长；
8. 候选文字、显式来源授权、三模式权重继承和禁止能产类推的既有门禁继续有效。

生成清单记录来源包、派生音元目录与布局文件的 SHA-256，并报告 18 个投影、3 个共享键位类、
15 个专用 Shift 键位类、15 个实际使用的特征规则和 131 条已投影记录。

本轮补齐规则明确采用以下边界：北京年轻人口语中的 `ie/üe + er` 投影到中央卷舌音元；`ian/üan`
投影到 `a˞`，与 `in/ün` 的中央卷舌结果分开；`o` 与 `ɤ` 归并后，`uo` 后两段投影到 `ɤ˞`。
`ao`、`ou`、`o`、`u` 暂只儿化后两段，第一段保持平舌。这最后一项是减少 Shift 层输入负担的
暂行输入投影约定，不声称完整描述其北京话表层音值；以后可只改派生规则和键位投影，不改来源记录。

## 5. 后续顺序

1. 可解释反查已在阶段 4B 完成：显示兼容拼音、儿化身份、派生音元和最终键位，不从键位反猜唯一音值；
2. 14 条原缺权重记录已从 PSC 低频外围层继承权重并通过三模式精确儿缀匹配门禁；
3. 原 42 条待决记录已按上述经审定规则完成投影；仍禁止由词尾“儿”或拼音 `r` 自动类推新增记录；
4. 在安装态观察 `Q/T/Y`、`V/C/X`、`P/A/Z` 的输入冲突和键感；出现问题时只调整键位投影，不改
   显式来源、派生音元身份或规范词典；
5. 能产儿化、自动增删“儿”和未写“儿”的口语提示仍不属于本阶段。

## 6. 回退

删除三个 `yime_erhua_mixed_*.dict.yaml` 的 schema 依赖即可整批关闭融合试点；删除融合路线时仍保留
规范词典和儿缀兼容输入。音元—键位投影文件是构建时来源，不由 PIME 在运行时读取，也不修改用户
词库或学习数据。

阶段 4B 见[融合儿化可解释反查](STAGE4B_ERHUA_REVERSE_LOOKUP.md)。
