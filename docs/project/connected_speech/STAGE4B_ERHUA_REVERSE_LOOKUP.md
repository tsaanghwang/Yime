# 阶段 4B：融合儿化可解释反查

## 1. 结论

阶段 4B 为已经进入三模式运行附加词典的融合儿化路线增加独立反查旁表。用户在反查工具中查询
“一阵儿”等试点词条时，可以同时看到：

- 保持不变的儿缀兼容拼音；
- “显式词汇化儿化”的读音身份和 PSC 儿化来源；
- 融合所附着的原音节；
- 用于现有布局投影的载体音元 ID；
- 儿化后的派生表层音元 ID；
- “表层音元 → 共享键位类 → 布局载体（物理键）”投影；
- 等长、变长、省键三种融合输入编码。

反查只解释已经生成的融合输入别名，不从按键反猜唯一音值，不改写规范词典、标准拼音注释、候选
文字或候选排序。

## 2. 数据边界

生成器写出 `yime_erhua_reverse_source.tsv`。当前文件为 1 行标题加 15 行数据，恰好对应三种运行
附加词典中实际获得既有权重的 15 个显式儿化词条。

旁表明确排除：

1. 14 条三模式规范词典均缺权重的延期记录；
2. 102 条 `suffix_only_encoding_pending` 记录；
3. 任何仅因词尾有“儿”或拼音含 `r` 而推测的能产儿化；
4. 两组仍标为 `research_only` 的鼻化卷舌音元。

因此，旁表的存在不会扩大可输入候选集合，也不会把研究态记录伪装成已实现能力。

## 3. 文件格式

每行包含 12 列：

| 列 | 含义 |
|---|---|
| `record_id` | 显式儿化记录 ID |
| `text` | 保持不变的候选文字 |
| `source_kind` | 来源类型，当前为 `psc_erhua` |
| `compatibility_numeric_pinyin` | 儿缀兼容数字标调拼音 |
| `surface_class` | 融合儿化表层类 |
| `attached_syllable_source` | 被儿化附着的原音节 |
| `carrier_yinyuan_ids` | 现有布局载体音元元组 |
| `surface_sound_unit_ids` | 派生表层音元元组 |
| `key_projection` | 表层音元到物理键的可解释投影 |
| `full_code` | 等长融合码 |
| `variable_code` | 变长融合码 |
| `shorthand_code` | 省键融合码 |

该文件由 `yime-erhua-mixed-derive` 与三种附加词典一起生成；文件 SHA-256 和行数写入
`yime_erhua_mixed_manifest.json`。不得手工维护或脱离同一生成过程单独改写。

## 4. 运行与回退

独立反查工具从共享运行数据目录读取旁表，普通系统词典反查仍走原链路。旁表缺失时按旧版本兼容
处理：普通反查继续可用，只是不显示融合儿化解释。旁表发生变化时反查缓存自动失效。

Rime 用户数据刷新会复制旁表，但它不参与 Rime 候选生成。删除旁表只能关闭融合解释；删除三个
`yime_erhua_mixed_*.dict.yaml` 的 schema 依赖才能关闭融合候选。两种回退边界彼此独立。

## 5. 完整性门禁

- 反查行数必须与实际继承权重并导出的词条数相等，当前均为 15；
- 每条必须具有记录 ID、显式来源、兼容拼音、附着音节、表层类、两套音元元组、键位投影和三模式码；
- 旁表哈希必须与生成清单一致；
- 三模式反查必须返回各自的融合码；
- 普通反查不得因旁表缺失而失败；
- UI 只在融合结果的详情区追加解释，不新增候选窗注释类别。

## 6. 下一步

1. 查明 14 条缺权重记录是否具备可进入规范候选库的独立来源；
2. 逐类审定 102 条待决融合记录；
3. `-ng` 鼻化卷舌类继续保持研究态，待音质映射、词条来源和碰撞报告共同通过后再申请试点；
4. 安装新构建后，在反查工具中用“一阵儿”核对三模式编码和完整详情。
