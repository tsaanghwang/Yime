## 1. 目标与边界

最终只维护 `Yime` 一个仓库：Windows 输入法继续使用 Go、C++/Rust 和 Rime 作为运行时；Python 仅保留为仓内的离线数据、词库、布局实验和验收工具，不进入安装包，也不再依赖 `pywin32`、`pynput`、Tk 或 PyInstaller 原型运行环境。

旧原型在退役期可以继续承担自身数据清理、历史核对和恢复现场维护，但它与 Yime 产品链单向隔离：
原型内的任何修改都不会被 Yime 自动发现、读取或导入。需要转移的新数据必须先取得明确授权，进入
非 Git 的内容锁归档，再由 Yime 独立审查；仓库边界和临时例外格式见
[YIME_REPOSITORY_DATA_BOUNDARY.md](YIME_REPOSITORY_DATA_BOUNDARY.md)。

迁移完成后，布局实验、效率评估和 Windows 发布必须读取同一份规范拼音、同一套音元编码规则、同一个布局真源和同一份核心词库选择。三种 Windows 模式继续由一份等长语义真源派生，不能恢复成三套人工维护码表。

本计划不授权：

- 直接合并任何分支到 `main`；
- 手写 Yinyuan ID、四音元码、拼音编码、键位或派生 Rime 词条；
- 为通过门禁而改写 baseline；
- 在迁移验收前删除原型数据库、备份、报告、构建目录或虚拟环境；
- 把 Python 运行时打进 Windows 安装包，或重写当前稳定的 Windows 输入路径。

## 4. 目标依赖链

迁移后只允许下面这条正向依赖：

```text
受控外部来源 + 已审查决定
  -> 规范带调拼音来源包
  -> 音节清单 / SyllableEncodingPipeline / YinjieEncoder
  -> 唯一语义编码真源
  -> 唯一布局真源 manual_key_layout.json
  -> 等长布局投影与核心词库选择
  -> Yime 仓内单一词库交接清单
  -> codemode 派生 full / variable / shorthand
  -> 真实 Rime 验收
  -> Windows 安装包

同一仓内的效率评估和布局试验
  -> 只读上述规范词库、规则和布局身份
  -> 输出独立实验报告，不反向修改规范来源
```

源文件、审查决定和规则是版本化输入；中间数据库、候选索引、报告、Rime 派生词典和安装包都是可再生输出。任何步骤不得从下游派生物反推并写回拼音或音元编码。

## 5. 分阶段实施

### Phase 0：词库身份与可复现性

- 已固定并校验所有生产输入，消除 `pinyin_hanzi.db` 的隐式可变依赖。
- 外部来源由 `external_inputs.lock.json` 锁定；运行数据库身份写入 v2 handoff evidence。
- 历史 1,167,501 与正式 1,166,753 的差异按旧目标记录保留，不把数量差直接归因于某一种音变。
- 已按用户批准以两次一致的正式流程结果晋升 baseline 和产品身份。

### Phase 1：建立 Yime 内离线工具边界

- 在 Yime 中建立独立的离线 Python 包、锁定依赖、工具入口和测试入口。
- Python 使用迁移时的最新稳定版本；不继承 Python 3.12 的 GUI/Windows-hook 限制。
- 把“源、审查决定、规则、生成物、外部大数据、报告”落实为不同目录和 Git 策略。
- Windows 正式构建必须能在不安装 Python 的情况下使用已验收交接物；只有更新交接物时才运行 Python 工具链。

### Phase 2：迁移规范编码和来源链

- 先迁移 `syllable/` 正式编码管线、音节来源/规范化、规则目录和唯一布局真源。
- 再迁移词库来源包构建、审查决定、输入模型、递归构词、容量、两级选择、排序和动态覆盖工具。
- 每个组件先在双仓上做黄金文件/哈希对照；对照通过后再把 Windows 导入入口切到仓内路径。
- 草稿、兼容实现和一次性调查脚本只能归档，不得成为新真源。

### Phase 3：收口单仓交接与三模式派生

- 用 Yime 仓内工具生成一份固定长度、带 manifest 的核心交接词典。
- 复用现有 Go `codemode` 派生三模式；Python 不生成三套独立维护词典。
- 删除导入脚本对 `C:\dev\Yime-python-prototype` 绝对路径的依赖。
- 保持候选分页、精确码注释、用户词典命名空间、布局摘要和安装包说明文件的既有门禁。

### Phase 4：迁移有效的评估与布局试验

- 迁移击键效率、候选窗口、布局比较、回放和报告工具中仍有产品价值的部分。
- 评估器必须通过同一 manifest 解析词库和布局，拒绝无身份或身份不匹配的输入。
- 实验布局只能产生候选 patch、摘要和对照报告；正式应用仍只能修改唯一布局真源并运行布局锁门禁。
- 原型 GUI、键盘 hook 和独立输入法运行壳不迁移。

### Phase 5：切换 CI、发布与文档

- 在 Yime CI 中增加离线工具单元测试、可复现重建、跨语言派生、真实 Rime 和安装包内容验收。
- 更新架构、Rime 集成、数据格式、工具策略和发布文档，去掉外部原型仓路径。
- 用全新 clone 验证“生成交接物”和“仅使用交接物构建 Windows 包”两条流程。

### Phase 6：冻结和退役原型

- 给原型最终提交打只读标签，记录其替代提交、最终 manifest 和恢复方式。
- 先保留远端只读归档；本地大文件先移动到有校验清单的外部归档，再按明确授权删除。
- `.generated`、`dist`、`build`、虚拟环境和重复数据库备份只有在恢复演练通过后才可清理。
- `tools/lexicon/restore_external_inputs.py` 从工作树外的归档恢复锁定输入，逐项验证大小和 SHA-256，并生成由完整发布验收入口强制读取的 JSON 证据；失败证据不得放行。
- 连续两个 Yime 发布周期无需回退原型后，才宣布退役完成。

## 6. 推荐的 PR 顺序

1. 合并独立 Windows 修复：`exact-composition-code`。
2. 合并独立测试工具：`sentence-segment-recorder`。
3. 审查并合并原型默认运行词库对齐；它用于过渡期评估一致性，不代表 Phase 0 已完成。
4. 合并本计划和清单。
5. 独立提交修复生产输入锁定与可复现构建日期，并保存双重重建证据。
6. 经批准以正式流程结果晋升 1,166,753 条 baseline；交接物、三模式、profile、manifest 和目标锁在同一生成链更新。
7. 按“规则与来源链 → 词库构建链 → 评估工具 → 文档/CI”的顺序逐组迁移。
8. 最后一个 PR 才移除跨仓导入路径；原型退役和磁盘清理在代码迁移之外单独执行。

每个 PR 都必须保持可回滚，且不得同时修改规范拼音、布局真源和发布词库身份三个维度。

## 7. 验收矩阵

| 门禁 | 必须证明 |
|---|---|
| 来源/规则 | 实例驱动音节清单、规则目录无 ID/键位第二真源、未知形式失败 |
| 布局 | 唯一布局真源、布局锁、三模式投影摘要一致 |
| 词库 | 同一输入锁连续重建哈希一致；词条差异有来源分类和批准 |
| 跨语言 | Python 语义交接与 Go `codemode` 三模式逐条一致 |
| 运行时 | Go 单测、真实 Rime、候选分页、精确码注释和用户词典回归通过 |
| 发布 | 包内词典、manifest、布局摘要和说明文件来自同一提交链；安装包不含 Python 运行时 |
| 评估 | 原型替代评估器读取与 Windows 相同身份，实验输出不回写真源 |
| 退役 | 全新 clone 可重建/发布，外部大数据可恢复，两个发布周期无需旧仓 |

## 8. 容量治理

迁移对象应以当前约 43 MB 的原型受跟踪源文件及其必要数据为主，而不是复制约 198 GB 工作树。现有大头包括约 107 GiB 的 `yime/`（其中备份约 98 GiB）、约 47 GiB 的 `.generated` 和约 38 GiB 的 `dist`；这些应分别进入外部归档、可再生缓存或删除候选，不得提交到 Yime Git 历史。

容量目标不是把 198 GB 搬进 7 GB 的仓库，而是让仓库只保存真源、规则、审查决定、小型固定测试样本和清单。大型语料与数据库使用内容寻址的外部存储和锁文件；正式交接词典按现有 Windows 发布策略保存，重复中间物按需生成。

## 9. 退役完成定义

只有同时满足以下条件，才能放弃原型仓：

- Yime 仓内可从锁定输入重建批准的规范词库身份；
- 三模式、布局试验和效率评估共用同一词库/布局 manifest；
- Windows 正式构建与安装包验收全部通过；
- 文档和 CI 不再引用原型绝对路径；
- 原型中仍有价值的工具和测试均已迁移或有明确归档决定；
- 大型外部数据有校验清单、来源说明和恢复演练；
- 远端只读标签和回滚说明存在，且连续两个发布周期无回退需求。
